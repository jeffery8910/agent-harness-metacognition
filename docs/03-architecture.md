# 3. 架構設計：誰有權判定、錯了怎麼回頭

前兩類規則靠 Agent「記得去做」。架構層把規則寫進系統結構，讓 Agent 就算忘了，系統也不會出錯。

---

## S1 判定權在伺服器

**規則**：會影響結果的關鍵判定（誰先、誰贏、是否通過），由伺服器根據自己觀察到的資料決定，不採信客戶端回報的值。

**實際案例**
- 猜歌搶答：約 70 人用手機搶答。判定誰先按，用的是伺服器（Cloudflare Durable Object）收到訊息的順序，不是手機傳來的時間戳。手機時鐘可能不準，也可能被改。同分時用伺服器記錄的總作答時間決定名次。

**和 Agent 的關係**：Agent 回報「測試通過」就像客戶端回報時間戳。真正的判定應該來自 CI、測試報告、線上 API 這種 Agent 改不了的來源。

**怎麼落地**：[server-authority/judge.mjs](../examples/server-authority/judge.mjs) 示範同一組搶答，用客戶端時間判和用伺服器時間判，會得到不同結果。

---

## S2 判定者與執行者分離

**規則**：負責產出的元件，不負責宣告自己成功。紀錄與狀態也要和執行環境分開存放。

**實際案例**
- 猜歌搶答：對戰紀錄存在獨立的 `Archive` Durable Object，和遊戲房間分開。房間出問題或被重建，歷史紀錄不受影響。
- 研究與文章：高風險的成果交給沒看過製作過程的審查 agent（見 [L2](04-learning.md#l2-獨立審查)）。

---

## S3 變更走 PR

**規則**：Agent 在獨立分支上改，送 PR 給人審核，不直接合併到主分支。

**實際案例**
- SolveMate：安全性升版照先前 PR #336 的慣例，改 Dockerfile、csproj、lock 檔，推到 `claude/` 開頭的分支再開 PR。
- 揪團日曆：從手動執行 `deploy.bat` 改成 GitHub 連動部署，`main` 分支更新才觸發 Cloudflare Workers Builds。部署有紀錄，也可以回到前一個 commit。

---

## S4 依外部節奏定期檢查

**規則**：依賴的上游有固定發布週期時，配合週期排程檢查，而不是等出事才查。

**實際案例**
- SolveMate 依賴 .NET，微軟每月第二個星期二發布安全更新。安全性檢查可以排在發布後一兩天，照 S3 的流程自動開 PR。

**注意**：排程任務是在沒人看著的時候執行，所以必須搭配 A1（前置檢查）和 S3（只開 PR，不合併）。
