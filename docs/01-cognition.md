# 1. 認知監控：我有多確定？

Agent 最危險的不是不知道，而是不知道自己不知道。這一類規則讓 Agent 在輸出時同時交代「把握程度」。

---

## C1 證據分級

**規則**：每個重要主張都標明證據等級。

| 等級 | 意思 | 必須附上 |
|---|---|---|
| `verified` 已驗證 | 有一手來源直接支持 | 來源連結 |
| `inferred` 推論 | 從證據推出來，沒有直接來源 | 推論依據 |
| `unverified` 未驗證 | 想查但查不到，或沒時間查 | 為什麼沒驗證 |

同時區分「已經發生」與「可能發生」。風險不等於事件。

**為什麼**：讀者分不出哪句是查證過的、哪句是推測，就會把推測當事實轉述出去。

**實際案例**
- 資安報導（BIND、PHP、eMudhra）固定把「已確認的漏洞與修補」和「可能的攻擊情境」分段寫，並提醒「使用 PHP 不代表有可利用的漏洞，更不代表已被入侵」。
- 查核社群貼文時逐句對照來源，例如一則 Linux 核心漏洞外洩的貼文，就拆出「蓄意外洩」、「可遠端利用」兩處誇大，以及一個其實屬於另一個專案的 CVE。
- 研究型頁面的參考文獻，標出哪些核對過摘要、哪些只憑既有知識。

**怎麼落地**：要求 Agent 用 [evidence-report](../examples/evidence-report/) 的格式輸出，再用 `check_evidence.py` 自動檢查：`verified` 沒附來源、`inferred` 沒寫依據，就擋下來。

---

## C2 交代沒驗證的範圍

**規則**：交付時固定附一段「沒驗證到的部分」，寫三件事：沒驗證什麼、為什麼、使用者可以怎麼補。

**為什麼**：「全部檢查過了，沒問題」和「能檢查的都沒問題，但有一塊沒辦法檢查」是完全不同的結論。後者如果省略，就會變成前者。

**實際案例**
- SolveMate 安全性更新：Agent 確認 .NET 執行環境、npm、KaTeX、GitHub Actions 都是最新版，但沙盒連不到 NuGet，沒辦法跑 `dotnet list package --vulnerable --include-transitive`。回報時直接寫明「間接相依套件沒有完整掃到」，並附上使用者可以在自己電腦跑的指令。

**怎麼落地**：evidence-report 的 `unverified_scope` 欄位是必填（可以是空陣列，但不能省略），逼 Agent 每次都想一次。

## C3 攤開決策理由

**規則**：在幾個方法之間做選擇時，列出候選方法、選了哪個、為什麼，以及各自適用的時機。

**為什麼**：只給結論，使用者沒辦法判斷 Agent 的取捨對不對，下次情境改變時也不知道該不該換方法。

**實際案例**
- SolveMate 的「分析與提醒」頁：每個模型（LSA、HMM、決策樹等）的結果都直接顯示在同一頁，並說明什麼情況用哪個模型。最後選定 SM-2 衍生特徵、LightGBM（DART）加單調性約束當主模型，LSA 降為描述性的探索工具，不當主要預測模型。

**怎麼落地**：在 CLAUDE.md 寫明「選方法時要列出候選與理由」；需要審查時，請 reviewer agent 檢查理由是否站得住。
