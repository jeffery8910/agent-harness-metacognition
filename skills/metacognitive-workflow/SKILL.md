# 後設認知工作流

目標：讓你在每一步都知道自己做了什麼、確定到什麼程度、哪裡可能錯，同時不讓小任務被流程拖慢。

## 0. 先判斷規模

| 任務 | 套用 |
|---|---|
| 問答、唯讀查詢、單一檔案的小修改 | 只用 R8 |
| 會改多個檔案、多步驟、要交付檔案 | R1–R6、R8–R11 |
| 不可逆或對外：部署、刪除、寄送、合併、發布、付款 | 全部，包括 R7 |

不確定屬於哪一級時，用較高的那一級。

## 工作迴圈

`界定範圍 → 前置檢查 → 執行 → 驗證 → 回報 → 沉澱`

## 規則

**R1 界定範圍**
開工前寫下四項：目標、排除項目、完成條件、輸出格式。完成條件要能用「是／否」判斷。
派子 Agent 時，四項都寫進它的指令。

**R2 前置檢查**
執行不可逆動作前，確認身分（登入帳號）、環境（分支、目錄、正式或測試環境）、目標（網址、資源 ID）。
任何一項不符就停止並回報原因。不要猜，不要換個指令硬做。
plugin 的 `preflight_deploy.py` hook 會在 `wrangler deploy` 前自動檢查 Cloudflare 帳號（需要設定 `EXPECTED_CF_EMAIL`）。

**R3 動作後驗證**
不要相信工具回報的「成功」。
- 寫檔或改設定：讀回比對。plugin 的 `verify_write.py` hook 會在 Write／Edit 後自動做；它回報失敗時，重新讀檔處理，不要回報完成。
- 部署：讀線上版本號或健康檢查端點。
- 切換類操作：操作前後各讀一次狀態。
同一個做法最多重試 2 次，之後換方法或回報。

**R4 用外部來源判定成功**
「成功」由你改不了的來源判定：測試或 CI 結果、線上 API、伺服器紀錄。你自己的敘述不算證據。

**R5 變更走分支與 PR**
開新分支、送 PR。不要直接推到主分支，不要自己合併。

**R6 留下痕跡**
三步以上的任務用任務清單，每完成一步就更新。腳本的 log 寫到不重複的檔名；不要等待使用者輸入，要能自己結束。

**R7 獨立審查**
高風險成果交付前，用 Agent 工具呼叫 `reviewer` 子 Agent。只給它成果路徑和原始資料，不給你的結論或製作過程。
處理它提出的每個「確認」等級問題；「疑似」等級要查證後決定。

**R8 回報時分級**
每個重要主張都歸入「已驗證（附來源）」、「推論（附依據）」或「未驗證（為什麼、怎麼補）」。區分「已經發生」與「可能發生」。
交付多步驟任務時，用 [report-template.md](report-template.md) 的格式。

**R9 寫出選擇理由**
在多個方案之間做選擇時，用一句話寫出候選方案和取捨。

**R10 沉澱經驗**
工具行為與預期不同時，在專案的 CLAUDE.md「已知陷阱」區塊加一行可以照做的規則，不要寫成事件紀錄。

**R11 主動更正**
發現先前說錯，明說哪一句錯、改成什麼。

## 不要做

- 唯讀的小任務不需要任務清單，也不需要分級報告的標題。
- 已經讀回確認過的，不要再讀一次。
- 不要把「沒有報錯」當成「成功」。
